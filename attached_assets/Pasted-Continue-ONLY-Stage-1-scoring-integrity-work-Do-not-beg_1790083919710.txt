The read-only verification found these blocking gaps:

1. Scorer start does not increment `scoring_version`.
2. Downstream participant/progression updates do not consistently increment versions.
3. Idempotent replay still runs bracket/tournament progression again.
4. Replay comparison excludes notes.
5. Replay returns current match state rather than the originally accepted result.
6. Server does not verify completed-leg winner against the score increment.
7. Server does not enforce `legHistory.length === scoreA + scoreB`.

Fix ONLY these Stage 1 blocking gaps.

## 1. Make all authoritative match mutations increment `scoring_version`

Any operation that changes authoritative scorer-relevant state on an existing match ID must increment `scoring_version`.

This includes at minimum:

* scorer start
* scorer restart
* admin score edit/reset
* participant changes
* group-to-knockout promotion changes
* knockout winner propagation
* third-place bracket repair
* any other existing route that changes:

  * scoreA
  * scoreB
  * status
  * winnerId
  * playerAId
  * playerBId
  * bestOf

Do not increment for non-authoritative presentation-only changes such as scorer display names.

Use shared helper logic where practical to avoid missing future writers.

The version must behave as an authoritative match revision.

---

## 2. Include status in scorer snapshot compatibility

Saved scorer state must also include and compare authoritative match status.

A snapshot created under `PENDING` must not be restored after the match transitions to `IN_PROGRESS` unless it was generated for that exact authoritative state/version.

A snapshot from a previously running match must not survive restart/reset/status changes.

Continue comparing:

* match ID
* player IDs
* bestOf
* confirmed scores
* scoring version

Add status to that compatibility contract.

---

## 3. Skip downstream side effects on idempotent replay

If `submitCompletedLeg()` returns:

`replayed: true`

the route must NOT repeat:

* knockout winner propagation
* group qualification/promotion
* tournament completion logic
* scorer assignment side effects
* duplicate Socket.IO completion side effects where those represent a newly completed leg/match

The retry should return the already-accepted submission result safely.

A lost-response retry must behave like:

“this leg was already accepted”

not:

“process match completion again”.

---

## 4. Store and return the original accepted replay result

Extend the idempotency submission record if required so the server can return the accepted submission result exactly as it was committed.

For an idempotent replay, return the originally accepted authoritative result, not whatever the match happens to look like after later legs.

At minimum preserve enough data to return:

* resulting scoreA
* resulting scoreB
* resulting scoringVersion
* status
* winnerId
* whether the accepted submission completed the match

If a safe additive migration is required, add it.

Do not rewrite old historical match data.

---

## 5. Strengthen replay payload comparison

The replay identity must include all client-controlled data that affects persistence.

Currently notes are excluded.

Canonicalize and compare the full persistence-relevant request, including:

* resulting score
* expected version
* completed leg
* statistics/note fields that are persisted

Do not allow:

same submission ID + same score + altered statistics

to be accepted as the same request.

Do not trust raw `JSON.stringify()` property ordering alone if a safer canonical comparison/hash is practical.

A stable normalized representation or stored request hash is acceptable.

---

## 6. Verify completed-leg winner matches score transition

For each accepted normal scorer leg:

If score transition is:

`A + 1`

then:

`completedLeg.winner` must be Player A / side A.

If score transition is:

`B + 1`

then:

`completedLeg.winner` must be Player B / side B.

Reject mismatches.

Also reject completed-leg data that references a player/side not belonging to the match.

Do this server-side.

---

## 7. Enforce legHistory/score consistency

Before accepting a new leg, verify authoritative persisted history is compatible with the authoritative score.

For fully recorded scorer matches:

`existingLegHistory.length === currentScoreA + currentScoreB`

After appending the accepted leg:

`nextLegHistory.length === newScoreA + newScoreB`

If this invariant is not true, do not silently append and continue.

Return a clear integrity error so the match can be repaired rather than made worse.

Be careful with legacy matches that may predate full `legHistory`.

If the application contains legitimate legacy matches without history, do not globally break them.

Instead design a safe compatibility rule such as:

* enforce strict invariant for matches that have entered the new scoring-integrity protocol / versioned submission system
* avoid pretending incomplete legacy history is valid
* surface legacy mismatch clearly

Explain the compatibility logic after implementation.

---

## 8. Make final-match progression atomic or safely resumable

The final-leg result currently commits before:

* knockout progression
* group-to-knockout promotion
* tournament completion

This can leave a completed match with broken downstream state.

Preferred solution:

Move required downstream progression and tournament-state updates into the same PostgreSQL transaction as the final-leg submission where technically practical.

If full transactional consolidation is too risky because existing progression logic is large or recursive, implement a robust transactional/resumable alternative that guarantees:

* a committed completed match cannot permanently lose its downstream progression
* retries are idempotent
* partial progression cannot silently remain indefinitely
* repeated execution is safe

Do not merely catch and log progression errors as non-fatal.

For final-leg completion, the API must not report ordinary success while required downstream state has silently failed.

If you choose a resumable design rather than a single transaction, explain exactly how it achieves equivalent consistency guarantees.

---

## 9. Version downstream matches when progression changes them

When progression places a player into a downstream match or resets that match’s authoritative state:

increment the downstream match’s `scoring_version`.

This applies to:

* winner advancement
* group qualification placement
* third-place bracket placement
* scorer assignment-related authoritative resets if they alter scoring identity/state

The downstream match revision must reflect that it changed.

## 10. Add real database-backed tests

Do not test against production tournament rows.

Create an isolated test strategy appropriate for the existing project.

Add tests that exercise real PostgreSQL transaction behavior, including at minimum:

### Concurrent version race

Two submissions target the same match/version concurrently.

Expected:

* exactly one succeeds
* exactly one conflicts
* one leg only is persisted

### Duplicate submission replay

Same submission ID sent twice.

Expected:

* one database submission row
* one legHistory append
* same accepted result returned
* no repeated progression

### Lost-response retry after later state change

Submission X succeeds.
Another legitimate submission changes the match.
Submission X is replayed.

Expected:

* no new leg
* original accepted result for X is returned or represented correctly
* current authoritative state is not corrupted

### Note persistence failure rollback

Force note write failure inside transaction.

Expected:

* no score change
* no version increment
* no submission row
* no history append

### Winner mismatch

Score says Player A won the leg.
Completed-leg winner says Player B.

Expected:

* rejected
* no state changes

### Existing history mismatch

Score/history are inconsistent for a new-protocol match.

Expected:

* submission rejected
* mismatch is not made worse

### Final-leg progression failure

Simulate downstream progression failure.

Expected:

* either entire operation rolls back
  OR
* resumable state is recorded and normal success is not falsely reported

### Scorer start version invalidation

Starting an existing match changes version.

Expected:

* old saved scorer snapshot becomes incompatible

Use a separate test database/schema/transaction strategy.
Do not create fake test data in live production tournament rows.
