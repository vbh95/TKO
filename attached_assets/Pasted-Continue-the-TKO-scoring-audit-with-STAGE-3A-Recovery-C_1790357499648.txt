==================================================
STAGE 3A TEST GROUP 1
SAME-SESSION STALE SNAPSHOT
==================================================

Highest priority.

Reproduce the scenario where two tabs effectively share the SAME
board-session identity/cookie.

Required sequence:

1. Start/recover the same match using the same valid scorer session.
2. Tab/request A obtains current unfinished-leg state.
3. Tab/request B obtains the same state.
4. A advances the unfinished leg and successfully persists the newer
   snapshot.
5. B still holds its older snapshot.
6. B attempts to persist that older but otherwise valid snapshot.
7. Read the durable current-leg state from the server/database.

The test must determine whether B can replace A's newer state.

Do not simulate this using two different scorer sessions because
Stage 2 already protects that case.

We specifically need SAME SESSION / STALE STATE.

Also establish the distinction between:

STALE WRITE
and
INTENTIONAL UNDO

because the eventual production protection must not prevent a valid
undo operation.

If current production behaviour allows the stale overwrite, the test
should fail for that exact reason.

Do not fix it yet.

STAGE 3A TEST GROUP 2
SCORER REMOUNT / AUTHORITATIVE HYDRATION
==================================================

Add focused scorer/client tests where practical.

Test recovery from server state for:

A. untouched active leg
B. partially played leg
C. checkout-ready unfinished leg
D. just-completed leg
E. fully completed match
F. state after admin reset
G. state after persisted undo

Verify:

- remaining scores
- visit history
- current thrower
- starter where applicable
- pending checkout state
- match score
- scoring version
- completed status

Most importantly:

Recovery/remount itself must NOT:
- create a visit
- create a leg
- resubmit a completed leg
- revert durable state
- reopen a completed match

Where possible, explicitly reproduce the stale-query-cache condition
identified in the Stage 3 assessment.

Do not redesign query behaviour yet.

==================================================
STAGE 3A TEST GROUP 3
SOCKET DISCONNECT / RECONNECT
==================================================

Test the active scorer behaviour across:

1. scorer is connected
2. scorer begins/continues an active match
3. socket disconnects
4. authoritative server state changes while disconnected
5. socket reconnects

Determine whether the scorer:

- rejoins the required scorer room
- refetches authoritative state
- reconciles active match state
- recognises ownership loss
- recognises version/reset changes
- avoids submitting stale local state

Also test:

disconnect
→ ownership invalidated/taken over
→ reconnect

The stale scorer must not silently regain write authority.

If room rejoining or active-state reconciliation does not happen,
capture that as a failing reproduction.

Do not fix socket behaviour yet.

==================================================
STAGE 3A TEST GROUP 4
LOST RESPONSE + PAGE REFRESH
==================================================

Test both distinct cases.

CASE A — ordinary lost HTTP response

Server successfully commits the completed leg but the client does not
receive the response.

Then simulate page refresh/remount.

Verify:
- exactly one completed leg exists
- authoritative match score is correct
- no duplicate leg can be produced
- scorer recovers to the correct current state

CASE B — commit succeeds but post-commit progression/side-effect fails

Use the existing Stage 1 failure mechanism if possible.

Sequence:

1. completed-leg transaction commits
2. progression/side-effect fails
3. client loses the useful response / refreshes
4. original in-memory submission ID is gone
5. scorer recovers from authoritative server state

Determine whether the outstanding post-commit work can ever be
completed after that refresh.

The purpose is NOT merely to check duplicate-leg protection.

We specifically need to prove or disprove the Stage 3 finding that
the original submission ID exists only in React memory and therefore
the recovery path may lose the ability to resume outstanding
post-commit processing.

Do not fix this yet.
