STAGE 3B.1 — Prevent Same-Session Stale Snapshot Overwrite

This is the first production fix from the completed Stage 3A verification.

Stage 3A confirmed that two tabs sharing the SAME valid board/scorer session can race within the same unfinished leg, and an older snapshot can overwrite newer persisted visit state.

This Stage 3B.1 task must fix ONLY that defect.

==================================================
CONFIRMED STAGE 3A DEFECT
==================================================

Confirmed behaviour:

1. Two tabs share the same valid board/scorer session identity.
2. Both load the same unfinished-leg state.
3. Tab A advances the leg and persists a newer valid snapshot.
4. Tab B still holds the older snapshot.
5. Tab B persists its older snapshot.
6. The older snapshot replaces the newer durable unfinished-leg state.

Existing scorer ownership checks do not prevent this because both tabs share the same valid session/lease.

Stage 1 completed-leg version/idempotency protections are not the issue.

Stage 2 ownership protections are not the issue.

The defect is specifically:
STALE WITHIN-LEG CURRENT-SNAPSHOT WRITE
from the SAME scorer session.

==================================================
CRITICAL REQUIREMENT
==================================================

Prevent an older/stale unfinished-leg snapshot from replacing a newer persisted snapshot.

BUT:

A legitimate intentional UNDO must still be possible.

Do NOT solve this by simply rejecting every snapshot containing fewer visits.

The system must be able to distinguish:

- stale/out-of-date write
from
- intentional undo/reset of the current unfinished leg

==================================================
IMPLEMENTATION APPROACH
==================================================

First inspect the Stage 3A same-session test and the existing current-leg persistence path.

Likely relevant files include:

- server/storage.ts
- server/routes.ts
- shared/schema.ts only if strictly necessary
- client/src/pages/scorer.tsx only if a request token/version must be supplied
- Stage 3A test files

Prefer the smallest concurrency-control mechanism that fits the existing architecture.

Potential acceptable approaches include a per-current-leg revision/version/generation value, compare-and-swap style protection, or another explicit stale-write token.

Do NOT choose an implementation merely because it is convenient.

The fix must provide these properties:

1. When a current-leg snapshot is read/recovered, the client/request has an identity for the revision it is based on.

2. Persisting a normal forward scoring change succeeds only if the stored current-leg revision still matches the revision the write was based on.

3. On successful persistence, the durable revision advances.

4. A stale same-session writer using the previous revision is rejected and cannot replace newer state.

5. The client can obtain/recover the new authoritative state after the rejection.

6. Intentional undo remains supported through an explicit valid path rather than looking identical to an accidental stale overwrite.

7. Ownership validation remains required.

8. Match scoringVersion protections remain required.

Do not remove or weaken any existing ownership/version/idempotency validation.

==================================================
UNDO REQUIREMENT
==================================================

Inspect how Undo currently persists state.

The fix must explicitly prove:

- normal forward update with current revision: accepted
- stale normal update with old revision: rejected
- deliberate undo from the current authoritative revision: accepted
- stale tab cannot masquerade as a legitimate undo

If Undo currently uses the same snapshot route, make the smallest change necessary to distinguish an intentional undo operation safely.

Do NOT redesign the scorer UI.

==================================================
ERROR HANDLING
==================================================

When rejecting a stale unfinished-leg write:

- return a clear conflict response, preferably HTTP 409 if consistent with the existing API
- include enough authoritative state or recovery information for the scorer to refetch/reconcile safely
- do not silently overwrite
- do not convert it into a generic server error

Use existing error conventions where possible.

Add or retain tests proving:

A. SAME-SESSION FORWARD RACE
- Tab A saves newer state
- Tab B submits older revision
- B is rejected
- A's newer durable state remains intact

B. LEGITIMATE UNDO
- latest valid scorer performs intentional undo

C. STALE TAB CANNOT UNDO

- current authoritative state remains unchanged

D. CURRENT WRITER CONTINUES
- after a successful write, client uses returned/new revision
- next valid write succeeds

E. RECOVERY
- stale writer can refetch/recover the authoritative current leg and continue only from the new revision
